## Ziel

Auf `main` liegt das Paket `tools/k3c-dev/internal/services` mit Konfiguration (`services.json`), einem Controller,
der je Dienst serialisiert startet, prüft, stoppt und mit Grenze neu startet, und einem Prozessbaum-Ende über ein
Windows Job Object. Noch ohne Übernahme, Metriken und MCP-Tools.

## Kontext

- Spec: `docs/backlog/B-067-dev-dienste.md` (Anforderungen › Konfiguration, Zustände, Ein Steuerpunkt, Beenden;
  Ausnahme- und Fehlerfälle; AC-01, AC-02) und die Sprint-README `docs/sprints/aktiv/M3-dev-dienste/README.md`.
- Stand nach M1/M2 (`docs/sprints/erledigt/`): Modul `tools/k3c-dev`; `internal/proc` startet ohne Konsolenfenster
  (`proc.Command(ctx, args)`, `npm` → `npm.cmd`) und beendet den Baum mit `taskkill /T /F` bzw. Prozessgruppe;
  `internal/console` (Ringpuffer je Quelle, `console.NewLineWriter`); eigenes Log über `*slog.Logger`.
- **Job Object** (Hinweis aus dem Review M1.4: `taskkill /T` folgt der Eltern-Kette, ein verwaister Enkel überlebt):
  in `internal/proc` unter Windows nach dem Start den Prozess einem Job Object mit
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` zuordnen (`golang.org/x/sys/windows`: `CreateJobObject`,
  `SetInformationJobObject`, `AssignProcessToJobObject`, `TerminateJobObject`). Beenden = `TerminateJobObject`,
  `taskkill /T /F` bleibt Rückfall, wenn die Zuordnung scheitert. Bonus: Stirbt `k3c-dev`, schließt Windows das Handle
  und die Dienste enden mit. Das kurze Fenster zwischen Start und Zuordnung ist hinzunehmen (Kommentar `ponytail:`).
  `check_run` nutzt denselben Weg (`proc.Command` bleibt die eine Stelle).
- **Konfiguration** `tools/k3c-dev/services.json`, gelesen mit `json.Decoder.DisallowUnknownFields`:
  ```json
  [
    { "name": "Vite", "command": ["npm", "run", "dev", "--", "--strictPort"], "cwd": ".", "port": 5173,
      "health": "http", "autoRestart": true },
    { "name": "Heimnetz", "command": ["npm", "start"], "cwd": ".", "port": 8080, "health": "http",
      "env": { "K3C_HTTP_PORT": "8080" } }
  ]
  ```
  `--strictPort`, weil Vite bei belegtem Port sonst still auf 5174 ausweicht und die Health-Prüfung einen fremden
  Prozess auf 5173 fragen würde. Heimnetz braucht einen Build (`dist/`); fehlt er, scheitert der Start mit der
  Ausgabe des Servers (kein Build-Schritt, B-067 › Nicht-Ziele). Fehler nennen Datei, Index bzw. Name und Feld.
- **Zustände** als Konstanten mit den deutschen Namen aus B-067 (`gestoppt`, `startet`, `läuft`, `übernommen`,
  `stoppt`, `fehlgeschlagen`); unbekannter Zustand kommt nicht vor.
- **Test-Nähte** statt echter Prozesse: `Starter` (startet und liefert Prozess mit PID, Warten auf Ende, Beenden),
  `Checker` (Health-Prüfung), Uhr/Timer. Produktion: `internal/proc` bzw. HTTP (`GET` mit 2 s Zeitlimit, 2xx/3xx) und
  TCP (`net.DialTimeout`).
- **Ablauf je Dienst** (ein Mutex je Dienst serialisiert Befehle aus Oberfläche und MCP): Start → `startet`, Ausgabe
  von stdout/stderr in den Konsolenpuffer unter dem Dienstnamen (`Reset` vor dem Start), Prüfung alle 1 s bis 60 s →
  `läuft` oder `fehlgeschlagen` (Baum beenden, Grund). Im Lauf eine Überwachung: Prüfung alle 10 s, drei Fehlschläge
  in Folge oder Prozessende → `fehlgeschlagen`; mit `autoRestart` neu starten, höchstens 3 Neustarts je 10 min
  (Zähler je Dienst sichtbar), danach bleibt `fehlgeschlagen`. Stopp → `stoppt`, Baum beenden, → `gestoppt`.
  Zustandswechsel als Rückruf `OnChange(Status)` und ins eigene Log (`ns=svc`).
- `Status` je Dienst: Name, Port, Health-Adresse, Zustand, PID, Start-Zeitpunkt, Neustarts, letzter Fehler.
  `StartAll` parallel, `StopAll` in umgekehrter Reihenfolge der Konfiguration.
- Budget: Datei ≤ 400, Funktion ≤ 60 Zeilen; Controller und Überwachung in getrennten Dateien.

## Ergebnis

- **AC-01 geprüft:** `internal/services/config_test.go` (die echte `services.json`, unbekanntes Feld, doppelter Name
  und Port, fehlendes Pflichtfeld, falscher Name, `health`, `log`, kein Array, fehlende Datei);
  `controller_test.go` mit gestelltem Prozess und gestellter Prüfung: Start → `läuft` mit Konsolenausgabe, zweiter
  Start abgelehnt, Stop beendet den Prozess (Zustände `startet läuft stoppt gestoppt`), unbekannter Dienst nennt die
  Namen; Zeitlimit, Startfehler und Prozessende beim Start → `fehlgeschlagen`; drei Abstürze → drei Neustarts, der
  vierte in 10 min bleibt `fehlgeschlagen`; drei Fehlschläge in Folge ohne Auto-Restart; `StopAll` rückwärts;
  `HealthCheck` gegen `httptest` (200, 302, 500) und einen TCP-Listener. Zehnfach wiederholt stabil.
- **Job Object:** `internal/proc/proc_test.go`: Kind startet einen Enkel und endet sofort, `Wait` räumt den Job ab,
  der Port des verwaisten Enkels ist danach zu (ohne Job überlebte er). `check_run` läuft über denselben `proc.Cmd`,
  seine Tests (Zeitlimit mit Enkel) sind weiter grün.
- Grün: `npm run check:dev` (inkl. staticcheck, unused), `npm run check`, `GOOS=linux GOARCH=arm64 go vet ./...`.
- **Abweichungen:** `Start-Commit` aus dem lokalen `main` (`9a85ce3`), kein Push. `proc.Cmd` bettet `exec.Cmd` ein und
  ersetzt `Start`/`Wait`/`Run`/`Kill`; unter Linux beendet `Wait` die Prozessgruppe genauso wie unter Windows der Job.
  `Stop` auf einen gestoppten oder fehlgeschlagenen Dienst ist kein Fehler (nichts zu tun). `force` für übernommene
  Dienste folgt mit der Übernahme in M3.2.
