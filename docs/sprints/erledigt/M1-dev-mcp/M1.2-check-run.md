## Kontext

- Spec: `docs/backlog/archiv/B-046-dev-mcp.md` › Anforderungen (`check_run`, Konsolenpuffer, `console_tail`), Beispiele,
  Ausnahme- und Fehlerfälle. Stand nach M1.1: `tools/k3c-dev/internal/mcpsrv/` mit Katalog, Zählern und Roundtrip-Test;
  neue Tools nur über den Katalog registrieren.
- Neues Paket `internal/console`: Ringpuffer je Quelle. Leser nutzen `bufio.Reader.ReadString('\n')` (nicht
  `bufio.Scanner`, der bei 64 KB still abbricht), `strings.ToValidUTF8`, Benachrichtigung über einen gepufferten Kanal
  mit `select … default` (ein langsamer Empfänger verliert Benachrichtigungen, nie Zeilen). Nach Prozessende erst
  antworten, wenn beide Ströme gelesen sind.
- Prozessbaum beenden in einem eigenen Paket `internal/proc` (M3 nutzt es für die Dienste, B-067): Windows
  `taskkill /T /F /PID <pid>`, sonst `Setpgid` und `syscall.Kill(-pid, SIGKILL)`, je eine kleine Datei mit Build-Tag. Unter Windows ohne Konsolenfenster starten (`CREATE_NO_WINDOW`). `npm` heißt `npm.cmd`.
- Verdichtung: pro Werkzeug eine Liste von Mustern für Fehlerzeilen, abgelesen an **echten** Läufen in diesem Repo
  (lokal einen roten Test bzw. Lint-Fehler erzeugen, Ausgabe gekürzt nach `tools/k3c-dev/internal/mcpsrv/testdata/`
  legen, Änderung danach zurücknehmen). Werkzeuge: Vitest, `tsc`, Oxlint, `go test`, `golangci-lint`, Vite-Build.
- Den Prozessstart als Funktionsvariable halten, damit Tests „kein Prozess startet“ zählen können; das Zeitlimit
  testet ein Kindprozess aus dem Test-Binary (Muster `TestHelperProcess`).
- `workbench_status` bekommt den letzten Lauf je Ziel (Exit, Dauer, Zeitpunkt).

## Ergebnis

- **AC-02 geprüft:** `check_test.go`: Ablehnung ohne Prozessstart für unbekanntes Ziel (nennt alle Ziele), Muster am
  falschen Ziel, jedes Sonderzeichen aus B-046 plus `< > % ^`, Leerzeichen und über 100 Zeichen, zweiter Lauf desselben
  Ziels (`läuft bereits`); Verdichtung an echten Läufen dieses Repos (`testdata/check/`: Vitest, tsc, Oxlint, go test,
  golangci-lint, Vite), grün = eine Zeile, rot ohne Muster = letzte 20 Zeilen, Deckel 60 mit `… N weitere`,
  Zeitlimit-Kopf; `runProcess` mit Test-Binary: Exit-Code und beide Ströme, fehlendes Programm, Zeitlimit beendet den
  Prozessbaum samt Enkel (unter 4 s statt Warten auf die offene Pipe). Ausgabe im Konsolenpuffer `check:<ziel>`.
- Von Hand (Agent, 2026-09-30): `go run .`, dann per MCP-Client über HTTP `check_run npm:test planning` →
  `npm:test · exit 0 · 1,9 s`, `pattern "a;b"` abgelehnt, `console_tail` zeigt die volle Ausgabe, `workbench_status`
  nennt den Lauf. Nicht über Claude Code selbst (das bräuchte einen Neustart der Sitzung mit `.mcp.json`).
- Grün: `npm run check:dev`, `npm run check`, `npm run check:go`, `GOOS=linux GOARCH=arm64 go vet ./...` im Modul.
- **Abweichungen:** Statt eigener `ReadString`-Leser bekommt `exec` einen Zeilen-`io.Writer` (`console.LineWriter`):
  So begrenzt `WaitDelay` hängende Pipes von Enkelprozessen, lange Zeilen bleiben trotzdem ganz. Nackte `FAIL`-Zeilen
  von `go test` zählen nicht als Fehlerzeile (Rauschen). `proc.Command` nimmt einen Context und beendet beim Abbruch den
  ganzen Baum; M3 nutzt es für die Dienste.
