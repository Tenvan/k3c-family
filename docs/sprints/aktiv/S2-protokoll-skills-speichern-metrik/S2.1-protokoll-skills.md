- **Status:** fertig
- **Typ:** Umsetzung
- **Agent:** autonom
- **Branch:** s2/1-protokoll-skills
- **Abhängig von:** S1 abgeschlossen (S1.5; gebraucht werden S1.1, S1.2a bis S1.2c und S1.4), F4.1 (Ereignisse im Protokoll, ändert dieselben Beispiele)
- **Tickets:** B-123
- **Kriterien:** AC-01, AC-02

## Ziel

Ein Gerät schickt je Slot Schlag und Skill-Slot in `input`, lernt Skills (`learn`) und setzt die Verteilung zurück (`respec`); der Zustand nennt je Spieler gelernte Skills, Slots, Abklingzeiten, freie Punkte und die gültigen Aktionen. Protokollversion 4, beide Enden, Dokument und Beispiele.

## Kontext

- **Protokoll heute (v3):** `docs/protocol.md` (Abschnitt „Nachrichten“, Tabelle; „Fehler-Codes“). Server: `engine/net/protocol.go` (`ProtocolVersion = 3`, `inMsg`, `inInput{Slot *int, MoveX, Sprint, Pay}`, `stateOf(w)` = `json.Marshal` der Welt ohne `seed`, `widthUnits`, mit `depth`, Feld `free` der Spieler gelöscht), `engine/net/dispatch.go` (`handle` → `roomMessage` → `input`: baut `sim.PlayerCommand{MoveX, Sprint, Pay}` je Slot, doppelter Slot → `room.ErrBadRequest`), `engine/net/ws.go` (`handshake`: `m.V == ProtocolVersion`, sonst Fehler `version` und Schließen). Raum: `engine/room/actions.go` (`Room.Input` prüft Slot des Geräts und `MoveX` auf NaN, begrenzt auf −1…1; `own(id, peer)` liefert das Gerät nur für die aktuelle Verbindung). Client: `src/online/clientProtocol.ts` (`PROTOCOL_VERSION = 3`, `SlotInput`, `ClientMessage`, `ServerMessage`, `WorldState`), `src/online/clientConnection.ts` (`RoomClient`: `sendInput`, `addSlot` …; 429 Zeilen inklusive Kommentaren, Oxlint zählt ohne Leer- und Kommentarzeilen bis 400), `src/model/types.ts` (`Player`). `src/online/protocol.ts` ist ein unbenutzter Rest von v1 (kein Import) und bleibt unverändert.
- **Beispiele:** `testdata/protocol/*.json`. Gelesen von `engine/net/ws_test.go` (`TestFormWieBeispiele`: Schlüssel jeder Server-Nachricht gegen `s2c-*.json`, bei `snap` nur die oberste Ebene von `s`) und `src/online/clientConnection.test.ts` (Import von `s2c-snapshot-*.json`, `s2c-joined.json`, `s2c-level.json`, `s2c-rooms.json`, `s2c-welcome.json`). Viele Tests senden `"v": 3` (`ws_test.go`, `clientConnection.test.ts`): auf die Konstante bzw. 4 umstellen.
- **Sim nach S1 (laut S1.1, S1.2a und S1.4 geplant, vor dem Start im Code prüfen; Namen im Code gelten):** `PlayerCommand.Attack bool` (JSON `attack`), `PlayerCommand.Skill int` (JSON `skill`, 0 = keiner, 1 bis 4 = Slot); `Player.Skills []string`, `Player.Slots []string` (Slot 1–4 = Index 0–3, leer = frei), `Player.Cooldowns []float64`, `Player.AttackCooldown float64` (alle `omitempty`, erscheinen also über `stateOf` ohne Code im Zustand, fehlen aber, solange sie leer sind); `World.SkillPoints` spiegelt den Insel-Pool `Island.SkillPool`; Funktionen `LearnSkill(w *World, p *Player, id string) error` und `Respec(w *World, p *Player) error` (Fehler bei unbekannt, schon gelernt, keine Punkte, Gating; Respec nicht am Tag oder nicht an der Burg). Verfügbare Punkte = Pool − Anzahl gelernter Skills (S1.1). Ein gesetzter `skill` feuert in jedem Tick, in dem der Slot bereit ist (S1.2a). Fehlt etwas davon im Code: `Status: blockiert` (`docs/arbeitsweise.md` › Wenn etwas nicht passt).
- **Spieler im Raum:** Monarch `i` ist der Insel-Spieler mit Index `i` (`r.isl.Players()[i]`), seine Stufe `r.isl.StageOf(i)`, die Welt `r.isl.Stages[…]`. Sim-Funktionen nur unter der Raum-Sperre aufrufen (wie `Tick`).
- **Entscheidungen dieser Session (Vorschläge der Planung, 🧑 bestätigt oder ändert sie mit der Spec-Freigabe; nicht als Beschluss behandeln):**
  - **Version:** `ProtocolVersion` 3 → 4 (B-123/AC-03). S2.4 bleibt auf 4 (siehe S2.4), solange zwischen S2.1 und S2.4 kein Release-Tag liegt.
  - **`input.p[]`** bekommt `attack` (bool, gehalten = Schlag, sobald bereit) und `skill` (Zahl 0–4, gehalten = Slot feuert, sobald bereit). Fehlen beide: `false` und `0` (ältere Eingabeformen bleiben gültig). `skill` außerhalb 0–4 → `bad_request`, die ganze Nachricht wird verworfen (alles oder nichts wie heute).
  - **Neue Nachrichten Gerät → Server:** `learn` (`slot`, `skill` = Skill-ID aus `data/monarch.json › skills`) ruft `LearnSkill`; `respec` (`slot`) ruft `Respec`. Slot nicht vom Gerät, fehlendes Feld oder ein Fehler der Sim → `bad_request` (kein neuer Fehler-Code; die Aktionsliste zeigt vorher, was geht). Erfolg hat keine eigene Antwort, der nächste Zustand zeigt die Änderung.
  - **Zustand je Spieler** (in `players[]` von `snap`/`delta`): `skills`, `slots`, `cooldowns`, `attackCooldown` wie von der Sim (fehlt = leer bzw. 0); neu vom Server berechnet `points` (verfügbare Punkte, immer gesetzt) und `actions` (immer eine Liste). Der Pool steht wie bisher in `skillPoints`.
  - **Aktionsliste** (B-123 › Offene Fragen: Umfang): nur der **Ort des Spielers**, keine Ziele anderer Stellen. Einträge `{ "action": "attack" }` (lebt, `attackCooldown` 0), `{ "action": "skill", "slot": n, "skill": id }` (Slot belegt, Abklingzeit 0, lebt), `{ "action": "learn" }` (`points` > 0), `{ "action": "respec" }` (Respec wäre erlaubt). **Keine Taste** (`key`) im Protokoll: die Belegung ist offen (Q06) und gehört dem Client (S3). Berufe, Tausch, Grabstein und Wiederbeleben kommen mit W5 und B-120.
  - **Regeln nicht nachbauen:** Für `respec` braucht die Liste eine Prüfung ohne Seiteneffekt. Bietet `engine/sim` eine (z. B. `CanRespec` o. ä.), sie nutzen; sonst `respec` nicht in die Liste aufnehmen, ein Ticket (Domäne SIM, „seiteneffektfreie Prüfung für Respec und Lernen“) anlegen und das im Ergebnis nennen. Die Nachricht `respec` wirkt trotzdem (Prüfung in `Respec`).
- Fallstricke: `ws_test.go` hat 390 Zeilen und `engine/room/room_test.go` 398: neue Tests in neue Dateien. `stateOf` darf die Welt nicht verändern (Kopie über JSON wie heute). Der Client rechnet nichts (`src/scenes` zeichnet nur), deshalb kommen `points` und `actions` vom Server. `src/scenes/` wird nicht geändert: neue Felder in `SlotInput` sind optional, damit `GameScene` unverändert kompiliert.
- Regeln: Protokolländerung nur in dieser Session, beide Enden (`docs/arbeitsweise.md` › Grenzfälle); Funktion ≤ 60 Zeilen, Datei ≤ 400; 2 Spieler je Gerät (Slots getrennt).
