# M9.1 · Checkout aus dem Header: Ursache klären, Antwort nennt den Checkout

## Ziel

Die Ursache, warum der Header `X-K3C-Root` aus Worktrees unter `.claude/worktrees/` nicht ankommt, ist geklärt und, soweit sie in `.mcp.json` oder k3c-dev liegt, behoben; jedes schreibende Tool nennt in seiner Antwort den Checkout, k3c-dev loggt je Aufruf, ob der Header da war.

## Kontext

- **Zuordnung heute:** `tools/k3c-dev/internal/mcpsrv/observe.go` (`observe`, eine Middleware für alle Tool-Aufrufe) ruft `resolveWorkspace` und legt den Checkout unter `wsKey{}` in den Kontext; die Tools holen ihn mit `s.ws(ctx)`. `resolveWorkspace` (`tools/k3c-dev/internal/mcpsrv/workspace.go`) fällt ohne Header **still** auf `s.cfg.Root` zurück; `workspaceOf` lehnt Ordner ab, die kein Checkout dieses Repos sind (`isWorktreeOf` liest `dir/.git` = `gitdir: <main>/.git/worktrees/<name>`). `workspace.label()` liefert „Repo-Wurzel …“ bzw. „Worktree <name> (…)“; `workbench_status` (`tools_status.go`) zeigt es in der Zeile `Checkout:`.
- **Header-Quelle:** `.mcp.json` setzt `"headersHelper": "node -p \"JSON.stringify({'X-K3C-Root': process.cwd()})\""`. Beobachtet (B-275 › Notizen, GR2.3, GR3.1, W3/PR #146, Desktop-App): aus einem Worktree meldete `workbench_status` `Checkout: Repo-Wurzel`, `plan_set` schrieb in die Wurzel. Ursache **ungeprüft**; vermutet: Die Desktop-App startet den `headersHelper` mit der Wurzel als cwd oder schickt den Header nicht. Mögliche Abhilfe, falls das stimmt: Der Helper nimmt statt `process.cwd()` eine Umgebungsvariable des Clients (z. B. `CLAUDE_PROJECT_DIR`, ungeprüft, ob die Desktop-App sie für Worktrees setzt) – erst messen, dann ändern.
- **Beschluss 🧑 2026-10-06 (Chat):** Fehlt der Header, schreibt ein schreibendes Tool (`plan_create`, `plan_set`, `plan_section`, `plan_delete`, `svc_start`, `svc_stop`; `svc_restart` gehört dazu) trotzdem in die Repo-Wurzel, nennt in der Antwort aber immer den Checkout. Es lehnt **nicht** ab.
- **Schreibende Tools:** `tools_planning.go` (`plan_create`, `plan_set`, `plan_section`, `plan_delete` über `planning.*(s.ws(ctx).root, …)`), `tools_services.go` (`svcStart`, `svcStop`, `svcRestart` über `serviceAction`). Die kleinste Stelle für „Antwort nennt den Checkout“ ist vermutlich eine Zeile in `observe` für eine feste Menge schreibender Tool-Namen; eine Zeile je Tool ist die Alternative. Erst prüfen, welche kleiner bleibt.
- **Log:** `observe` loggt heute `📨 <tool>: start` (Debug) mit `ns=mcp`. Neues Attribut (z. B. `header=true|false`, `checkout=<label>`) an dieser Zeile oder an `finish`; Emoji-Regel aus `CLAUDE.md` beachten.
- **Tests:** `tools/k3c-dev/internal/mcpsrv/workspace_test.go` (`TestWorkspaceAusHeader`, `TestWorktreeTrenntKonsoleUndDateien`, `TestWorktreeDiensteMitEigenenPorts`) baut Worktrees im Temp-Ordner; neue Fälle dort, Datei bleibt ≤ 400 Zeilen.
- **Fallstrick:** Diese Session läuft selbst in einem Worktree; k3c-dev kann darum die Wurzel bedienen (Memory „k3c-dev im Worktree prüfen“). Zuerst `workbench_status`; nennt es nicht diesen Worktree, alle Prüfungen in der Shell (`task check:dev`, `task check`). Firewall-Regel: Proben nur auf Loopback, kein `go run`.
