## Ziel

`PlayerInput` kennt die Aktionen Schlag, Skill 1–4 und Skill-Menü auf Controller, Tastatur und Touch; eine reine, getestete Funktion liefert die Slot-Belegung je Gerät, und `GameScene` schickt `attack` und `skill` im `input` an den Server.

## Kontext

- **Belegung (beschlossen, Q06; `docs/rules/monarch.md` § 4):** Controller Schlag **X**, Slots 1–4 **LB, RB, LT, D-Pad hoch**, Skill-Menü **D-Pad runter**, Bau-Menü Y, Vollbild Stick drücken. Tastatur Schlag **E**, Slots **Q, R, T, Z**, Skill-Menü **K**. Touch: eigene Tasten im Touch-Overlay. **B** bleibt unbelegt, **View + Menu** gemeinsam reserviert, LS-Klick bleibt Debug-Overlay (nur Dev). Achtung: D-Pad links/rechts läuft heute (`moveX`), D-Pad hoch/runter sind frei.
- Code: `src/input/playerInput.ts` (`Action`-Typ, `PAD_ACTIONS`, `GamepadInput`, `KeyboardInput`; heute `interact` = X/E, `skillMenu` = View/K, `pause` = Menu), `src/input/touchInput.ts` (DOM-Overlay, `TouchKey`, Tasten `confirm`, `sprint`, `fullscreen`). `src/input/` ist Domäne PLAT; die Freigabe dieser Spec erlaubt die Änderung (S3-README › Regeln).
- `skillMenu` wandert von View auf D-Pad runter: View allein bleibt danach frei (View + Menu reserviert). Pause/Menü gehört S5 (Q01: Menu kurz öffnet das Menü); läuft S5 vorher, deren Stand in `playerInput.ts` übernehmen, nicht überschreiben.
- **Protokoll (aus S2.1, geplant; Namen im Code gelten):** `input.p[]` mit `attack` (bool, gehalten) und `skill` (0–4, 0 = keiner); Client `src/online/clientProtocol.ts` (`SlotInput`), `src/online/clientConnection.ts` (`sendInput`). Fehlen die Felder im Code: `Status: blockiert`.
- Slot-Belegung als reine Funktion (z. B. `src/input/slotBindings.ts`): Gerät (`pad`, `keyboard`, `touch`) → Liste der Tasten je Aktion (Schlag, Slot 1–4, Menü) mit Anzeigetext; sie dient auch dem Overlay (S3.3) und den Glyphen (S6). Keine Taste doppelt, B nie, View/Menu nie allein.
- `src/scenes` rechnet nichts (`src/scenes/noSim.test.ts`); 2 Spieler je Gerät (`localSlots.ts`).
