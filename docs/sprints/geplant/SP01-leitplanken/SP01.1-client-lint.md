## Ziel

Oxlint prüft das Komplexitäts-Budget für allen TypeScript-Code. `npm run check` bündelt Lint, Typecheck und Tests
und läuft in der CI.

## Kontext

- Budget (harte Grenzen) aus `docs/arbeitsweise.md` › Komplexitäts-Budget: Datei 400 Zeilen, Funktion 60 Zeilen
  (nur Code, nicht Tests), Verschachtelung 4, zyklomatische Komplexität 15 (nur Code). Die Zielwerte (300/40/3/10)
  prüft das Review, nicht der Linter.
- Das Projekt nutzt **TypeScript 7** (`package.json`), das **keine JS-API** hat (`require('typescript').createSourceFile`
  ist `undefined`). `typescript-eslint` funktioniert damit nicht. Deshalb **Oxlint** (eigener Parser, eine Abhängigkeit).
  Oxlint kennt die Regeln `max-lines`, `max-lines-per-function`, `max-depth`, `complexity` (Option `max`).
- Bekannte große Dateien (Stand SP00): `src/scenes/worldRenderer.ts` 383, `src/scenes/GameScene.ts` 371,
  `src/tools/gamepadTest.ts` 332, `src/tools/spriteReference.ts` 330, `src/landing/landing.ts` 319 Zeilen (alle < 400).
  Welche Funktionen über 60 Zeilen oder Komplexität 15 liegen, ist unbekannt: das misst diese Session.
- CI: `.github/workflows/ci.yml`, Job `check`, Schritte `npm ci`, `npm run typecheck`, `npm test`, `npm run build`.
- Die erste Session des Sprints setzt `Start-Commit` in `docs/sprints/aktiv/SP01-leitplanken/README.md`.

## Nicht-Ziele

- Keinen Code umbauen, um Regeln zu erfüllen. Verstöße im Bestand werden Ausnahmen (Ratsche).
- Keine Stil-Regeln (Formatierung, Benennung). Nur das Budget plus Oxlints Standard-Regeln der Kategorie `correctness`.

## Schritte

1. `git rev-parse --short origin/main` → in der Sprint-README als `Start-Commit` eintragen.
2. `npm install --save-dev oxlint` (aktuelle Version).
3. `.oxlintrc.json` anlegen: `ignorePatterns` für `dist`, `dist-server`, `node_modules`, `public`; Regeln als `error`:
   `max-lines` `{ "max": 400, "skipBlankLines": true, "skipComments": true }`,
   `max-lines-per-function` `{ "max": 60, "skipBlankLines": true, "skipComments": true }`,
   `max-depth` `{ "max": 4 }`, `complexity` `{ "max": 15 }`.
   Override für `**/*.test.ts` und `tests/**`: `max-lines-per-function` und `complexity` aus.
4. `npx oxlint` ausführen. Für **jede** Datei mit Verstoß einen Override nur für diese Datei anlegen, der die Grenze auf
   den gemessenen Wert hebt (Ratsche). Kommentar im Override: `Ratsche: nur senken`.
   Sind es mehr als 15 Overrides: trotzdem anlegen und im Ergebnis melden (Grenzen prüft das Review).
5. `package.json` Skripte: `"lint": "oxlint"`, `"check": "npm run lint && npm run typecheck && npm test"`.
6. `ci.yml`: Schritt `- run: npm run lint` direkt vor `npm run typecheck`.
7. `CLAUDE.md` › Befehle: Zeile `npm run check    # Lint + Typecheck + Tests (vor jedem Abschluss)`;
   Satz „Vor jedem Abschluss: `npm test` und `npm run typecheck`“ → „Vor jedem Abschluss: `npm run check`“.
8. Probe: Datei `src/world/_probe.ts` mit einer Funktion aus 61 Anweisungszeilen anlegen, `npm run lint` muss mit
   Exit-Code ≠ 0 scheitern. Probe wieder löschen.

## Fertig, wenn

- [ ] `npm run check` endet mit Exit-Code 0
- [ ] Probe aus Schritt 8 ließ `npm run lint` scheitern und ist gelöscht (`git status` zeigt sie nicht)
- [ ] `.oxlintrc.json` enthält für jede Ausnahme Datei und gemessenen Wert; Liste im Ergebnis
- [ ] CI-Lauf des PR ist grün
- [ ] `Start-Commit` in der Sprint-README gesetzt
