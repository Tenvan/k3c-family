## Ziel

`k3c_kit::mcp` ist ein vollständiger MCP-Server auf `rmcp` 3.11 (Streamable HTTP an 127.0.0.1, `/mcp`) mit den Eigenheiten von `workkit/mcpkit`: Checkout je Aufruf, Parameter-Hinweis, Checkout-Zeile schreibender Tools, Panik als Fehler, Zähler, Aufruf-Log, Nutzungsstatistik, Fortschritt, erzwungenes chunked, Neustart ohne Verlust der Zähler.

### Vorentscheidungen (Claude, nach Leitfaden)

1. **Tools schreiben die Apps mit den rmcp-Makros** (`#[tool_router]`, `#[tool]` auf ihrem eigenen Typ, Argumente `Parameters<T>` mit `schemars::JsonSchema`), wie im Spike. `k3c-kit` liefert keinen `#[tool_handler]`, sondern einen eigenen Dienst: `pub struct Server<A: Clone + Send + Sync + 'static>`; `Server::new(opts: Options, app: A, tools: ToolRouter<A>, prompts: Option<PromptRouter<A>>) -> Arc<Server<A>>`. Pro MCP-Session baut die Fabrik von `StreamableHttpService` ein `KitService<A>` (Clone, hält `Arc` auf den gemeinsamen Kern) und implementiert `rmcp::ServerHandler` von Hand: `get_info` (Name, Version, Instructions, Fähigkeit tools, prompts nur mit PromptRouter), `list_tools` (`tools.list_all()`, das schon nach Namen sortiert wie das Go-SDK; bei `takes_checkout` das Schema mit `with_checkout` ergänzen), `call_tool` (Ablauf aus `observe.rs`), `list_prompts`/`get_prompt` (an den PromptRouter; das Studio braucht Prompts, `tools_assets_prompts.go`), `on_initialized` (Clients zählen wie `InitializedHandler`).
2. **`Options`** (alle Funktionen optional, `Arc<dyn Fn … + Send + Sync>`): `name`, `version`, `instructions`, `root`, `port: u16` (0 = frei, Tests), `env_port`, `log: Logger`, `on_start`, `on_call`, `usage: Option<Arc<usage::Tracker>>`, `takes_checkout`, `write_tool`, `target`, `track: Fn(&str) -> Box<dyn FnOnce() + Send>`, `mount: Fn(axum::Router) -> axum::Router` (statt `*http.ServeMux`, `/mcp` belegt), `before_stop`, dazu neu `catalog: Vec<String>`: Reihenfolge für `Stats::register` wie die Registrierung in Go (leer = alphabetisch; Namen ohne Route ignorieren, Routen ohne Namen alphabetisch anhängen), weil `ToolRouter` die Reihenfolge nicht kennt.
3. **Server-Methoden** wie Go: `resolve_port(env, raw, def) -> Result<u16, String>` (frei, Text wortgleich), `start().await` (Bind 127.0.0.1, Fehlertext „port %d nicht verfügbar (…); einen anderen Port über %s setzen“, bei laufendem Server „server läuft bereits“), `stop().await` (`before_stop`, Abbruch über `StreamableHttpServerConfig::cancellation_token`, axum graceful shutdown mit höchstens 2 s, danach Sessions leeren), `restart().await` (Log-Meldungen wortgleich mit `ns=mcp`), `url()`, `stats().await` (Clients frisch zählen), `calls()`, `uptime()`, `clients().await` (`LocalSessionManager.sessions.read().await.len()`), `root()`, `own_checkout(&Workspace) -> bool`. Je `start` ein neuer `LocalSessionManager` mit `session_config.keep_alive = Some(30 min)` (Go `sessionTimeout`); Host-Schutz von rmcp bleibt Vorgabe.
4. **Ablauf je `tools/call`** (Port von `observe.go`, Reihenfolge einhalten): Kopf `X-K3C-Root` aus `ctx.extensions.get::<axum::http::request::Parts>()`; `Resolver::resolve_header`; bei `takes_checkout` `split_checkout` und ggf. `resolve_checkout`; `Workspace` und `Progress` in `ctx.extensions` einfügen (Tools lesen sie mit `Extension<Workspace>`/`Extension<Progress>`); `track("tool:<name>")`; `stats.begin`; Debug-Log „📨 <tool>: start“ mit `ns`, `tool`, `args` (gekürzt); bei Checkout-Fehler Fehler-Ergebnis; Prüfung unbekannter Felder (Punkt 5); Aufruf; `add_param_hint`; `add_checkout`; `finish` (Stats, Log „❌ <tool>: <Fehler>“ als Warn bzw. „✅ <tool>: ok“ als Info mit `ns`, `tool`, `ms`, `ok`, `header`, `checkout_arg`, `checkout`; `usage.record` nur für Tools aus dem Katalog).
5. **Unbekannte Felder:** Das Go-SDK lehnt sie per Schema ab, `rmcp` ignoriert sie. Darum prüft `observe` die Argument-Schlüssel gegen die Eigenschaften des Eingabe-Schemas (dieselbe Quelle wie Go `jsonNames`) und liefert bei Fremden das Fehler-Ergebnis mit **demselben Text wie das Go-SDK** plus die Zeile „gültige Parameter: …“. Den Text ermittelt die Session aus den Go-Quellen: Versionen in `tools/workkit/go.mod`, Ordner `$(go env GOMODCACHE)`, dort `github.com/google/jsonschema-go@<v>/jsonschema/validate.go` („additional properties“) und die Umhüllung in `github.com/modelcontextprotocol/go-sdk@<v>/mcp/` (`grep -rn "validating"`). Ebenso prüft sie dort, ob ungültige Argumente (falscher Typ) im Go-SDK ein Fehler-Ergebnis (`IsError`) oder ein Protokollfehler sind, und bildet das nach (rmcp meldet `invalid_params`).
6. **Panik:** Der Aufruf läuft per `tokio::spawn` mit geklontem `app` und `Arc<ToolRouter<A>>`; `JoinError::is_panic()` wird zum Fehler-Ergebnis `"{PANIC_TEXT}: {Nachricht}"` (Payload `&str`/`String`), der Server läuft weiter. Kein `futures`-Crate.
7. **Fortschritt:** `#[derive(Clone)] pub struct Progress` mit `none()`, `from_fn(Arc<dyn Fn(&str, Duration) + Send + Sync>)` (Go `WithProgressFunc`, Tests), `is_active()`, `report(&self, msg, elapsed)` (sendet bei `progressToken` aus `ctx.meta` über `ctx.peer.notify_progress` mit `progress = elapsed` in Sekunden, Fehler verworfen, nicht blockierend per `tokio::spawn`).
8. **chunked:** `chunked::force_chunked` als axum-Middleware um den `StreamableHttpService`: Antworten ohne `text/event-stream`, Status ≥ 200, nicht 204/304, verlieren `Content-Length` und bekommen einen Stream-Body (`Body::from_stream(body.into_data_stream())`), damit hyper chunked sendet. Begründung aus `chunked_writer.go` als Kommentar übernehmen.
9. **Hilfen aus `tool.go`:** `read_only() -> ToolAnnotations` (read_only, idempotent, open_world false) und `image_result(png: &[u8], text: &str) -> CallToolResult` (Bild `image/png` plus Text); dazu `base64 = "=0.22.1"` (Version aus dem Spike-Lockfile, MIT/Apache, verbreitet; im Ergebnis melden). Dev-Abhängigkeit `reqwest = { version = "=0.12.28", default-features = false, features = ["json"] }`, `axum = "=0.8.9"` als normale Abhängigkeit.

### Pflicht-Tests (`server_tests.rs`, Test-App mit `#[tool_router]`)

Tools `echo` (lesend), `schreib` (schreibend, mit `checkout`), `panik`, `fortschritt`; Server auf Port 0. Geprüft: `initialize` liefert Name und Instructions; `notifications/initialized` → 202; `tools/list` sortiert, `schreib` hat `checkout` im Schema, `echo` nicht; `echo` antwortet; unbekanntes Feld → Fehler-Ergebnis mit Go-Text und „gültige Parameter: …“; `panik` → `PANIC_TEXT`, danach antwortet `echo` weiter; `schreib` endet mit „Checkout: …“; Kopf `X-K3C-Root` auf fremden Ordner → Fehler-Ergebnis; Zähler und Aufruf-Log nach drei Aufrufen; `usage.record` nur für bekannte Tools; `restart` behält die Zähler; nach `stop` ist `url()` leer und `clients()` 0. `chunked_tests.rs` portiert `TestBenachrichtigungAntwortIstChunkedAbgeschlossen` mit rohem `tokio::net::TcpStream` (Kopf `Transfer-Encoding: chunked`, kein `Content-Length`, Abschluss `0\r\n\r\n`).

### Für den Hauptrechner
- Auflage für RU69/RU70: unbekannte Felder werden nur auf oberster Ebene abgelehnt. Verschachtelte Typen brauchen `deny_unknown_fields` (z. B. `world_story_set`), sonst meldet Rust bei Tippfehlern Erfolg.
- `stop` trennt offene Verbindungen nicht hart (Go: `Close()` nach der Frist).
- Falscher Typ oder fehlendes Pflichtfeld: `IsError` wie Go, aber Text `failed to deserialize parameters: …` (Leitfaden verlangt gleichen Antworttext); `null` bei `Option` ungeprüft. Bei zwei Fehlern zugleich meldet Rust das unbekannte Feld, Go den Typ.
- `tools/list` ohne `additionalProperties:false`; Argumente, die kein Objekt sind, ungeprüft; Log und Statistik erhalten neu serialisierte Argumente.
- 30-Minuten-Frist ist eine Leerlauffrist, auch während eines laufenden Aufrufs; Fortschritt kurz vor dem Ergebnis kann verloren gehen.
- pprof-Port (RU69) muss `loopbackOnly` mitbringen: `mount`-Routen haben keinen Host-Schutz aus dem SDK.
- Tools geben Fehler als `Result<_, String>` zurück; sie haben keinen Zugriff auf `Server` (`own_checkout`: App hält ihre Wurzel selbst).
- Ungeprüft: Prompts mit `PromptRouter`, Host-Schutz, echter Claude-Code-Client, Netzwerkfilter.
