# M3.2 · Übernahme, Port belegt, Metriken und Log-Level je Dienst

- **Status:** offen
- **Typ:** Umsetzung
- **Agent:** autonom
- **Branch:** m3/2-uebernahme-metriken
- **Abhängig von:** M3.1
- **Tickets:** B-067
- **Kriterien:** AC-02, AC-03

## Ziel

Der Controller übernimmt beim Start schon laufende Dienste, erkennt einen fremd belegten Port, liefert PID, CPU,
Speicher und Laufzeit je Dienst und zählt die Log-Level der letzten 60 min; die Ausgabe der Dienste erscheint in
`logs_sources`.

## Kontext

- Spec: `docs/backlog/B-067-dev-dienste.md` (Übernahme, Port belegt, Metriken, Konsole, Log-Level-Zähler; AC-03,
  AC-04, AC-06). Stand nach M3.1: `internal/services` (Konfiguration, Controller, Zustände, Test-Nähte), Job Object.
- **Abhängigkeit** `github.com/shirou/gopsutil/v4` (v4.26.8 geprüft 2026-09-30, von 🧑 mit der Sprint-Freigabe genehmigt).
  Port → PID: `net.ConnectionsWithContext(ctx, "tcp")`, Eintrag mit `Status == "LISTEN"` und `Laddr.Port`. Metriken:
  `process.NewProcessWithContext`, `CPUPercentWithContext` (zwischen zwei Messungen), `MemoryInfoWithContext().RSS`,
  `CreateTimeWithContext` → Laufzeit. Alle 2 s für `läuft` und `übernommen`, sonst leer. Fehler einer Messung (Prozess
  weg) lassen den letzten Wert stehen, statt den Zustand zu ändern; das entscheidet die Überwachung aus M3.1.
- **Übernahme** (`Adopt` beim Programmstart, vor jedem Befehl): besteht die Health-Prüfung eines Dienstes, wird er
  `übernommen` mit PID über den Port; kein Konsolenpuffer-Anschluss, kein Auto-Restart, Überwachung nur per Prüfung
  (Fehlschlag → `gestoppt` mit Grund `übernommener Prozess nicht mehr erreichbar`). Stopp nur mit `force`: beendet den
  Baum der PID (`proc.KillTree`, das Job Object gilt nur für eigene Prozesse).
- **Port belegt:** vor jedem Start den Port prüfen (TCP-Verbindung gelingt) → `fehlgeschlagen` mit
  `Port 8080 bereits belegt (PID 8812)` (PID über gopsutil, sonst `PID unbekannt`), kein Prozess startet.
- **Konsole:** die Puffer der Dienste liegen schon seit M3.1 im gemeinsamen `console.Store`; `logs_sources` und
  `console_tail` (`internal/mcpsrv/tools_logs.go`, `tools_console.go`) zeigen sie ohne Änderung. Test, dass ein
  gestarteter Dienst dort als `Konsole Vite · n Zeilen` erscheint.
- **Log-Level-Zähler:** für Dienste mit `log` die Einträge je Level der letzten 60 min aus `logs/<log>.jsonl` über
  `internal/logs` (`Scan` mit `Since`, Budget wie dort), Ergebnis `map[Level]int` plus `budgetHit`; bei Bedarf gerechnet,
  nicht im Hintergrund. `k3c-server` bekommt `log` erst mit SP03 (B-066); Test mit einer Beispieldatei.
- Test-Nähte für gopsutil (`PortPID`, `Metrics` als Funktionen), damit Übernahme und `Port belegt` ohne echte Ports
  testbar sind; ein Test gegen einen echten Kindprozess prüft die gopsutil-Anbindung (B-067/AC-04).

## Schritte

1. `go get github.com/shirou/gopsutil/v4@v4.26.8`.
2. Port → PID, Metriken, Übernahme, `Port belegt` im Controller.
3. Log-Level-Zähler je Dienst.
4. Tests: Übernahme (Prüfung besteht → `übernommen` mit PID, kein Auto-Restart, Stopp ohne `force` abgelehnt, mit
   `force` beendet), `Port belegt` ohne Prozessstart, Metriken gegen einen echten Kindprozess (PID stimmt, RSS > 0,
   Laufzeit wächst), Konsolen-Quelle in `logs_sources`, Log-Level-Zähler an einer Beispieldatei mit Einträgen innerhalb
   und außerhalb der 60 min.
5. `npm run check:dev` und `npm run check` → grün. Ergebnis ausfüllen, lokal mergen.
