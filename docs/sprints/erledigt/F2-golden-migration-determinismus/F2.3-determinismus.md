## Ziel

Ein Check schlägt an, wenn Spielzustand von einer Map-Iteration abhängt, und ein Test belegt, dass ein künstlich verlangsamter Raum-Takt nach 600 Ticks denselben Weltzustand ergibt wie ein schneller.

## Kontext

- Go iteriert Maps zufällig. `engine/sim` und `engine/level` sollen deterministisch sein (`CLAUDE.md`, nur `engine/rng`). Maps im Zustand: z. B. `Campaign.worlds` und `pendingHubs` als `map[int]…` (`engine/sim/save.go`), `type Event map[string]any` (`engine/sim/types.go`).
- Der Raum-Takt ist ein `time.Ticker` (`engine/room/run.go`, `Room.run`, `safeTick`); `Room.Tick()` rechnet einen Schritt mit `1.0/TickHz` (`engine/room/actions.go`). Die Tests in `engine/room/run_test.go` takten Räume von Hand (`world(t, r)` liefert den Zustand als JSON, Hilfsfunktionen `setup`, `ok`, `need`).
- Linter-Konfiguration: `.golangci.yml` (INF); ein eigener Test über `go/parser` ist ohne neue Abhängigkeit möglich (`tests/nesting_test.go` ist das Vorbild für einen Quelltext-Check in Go).
- Ein reines `for … range` über eine Map ist nur dann ein Befund, wenn die Reihenfolge das Ergebnis beeinflusst; harmlose Fälle (z. B. Summe, vorher sortierte Schlüssel) stehen in der Ausnahmeliste mit Begründung.
- Findet der Check echte Treffer im bestehenden Code, wird jeder Treffer **kein** Produktionscode-Fix in dieser Session, sondern ein Ticket (Domäne SIM) und ein Eintrag in der Ausnahmeliste mit „Ticket B-…“.
