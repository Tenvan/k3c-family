# SP11.1 · Image im Registry veröffentlichen, Compose auf `pull` umstellen

## Ziel

Ein Tag `v*` baut das Docker-Image für `linux/amd64` und `linux/arm64` und legt es im Registry ab; `compose.yaml` zieht dieses Image, sodass `docker compose pull` auf dem Pi die neue Version holt. Gebaut wird nicht mehr auf dem Pi.

## Kontext

- Heute baut `compose.yaml` das Image selbst (`build: .`, `image: k3c-server`). `docker compose pull` hat dann nichts zu holen (B-035/AC-02 wäre unerfüllbar), und ein Build auf dem Pi (npm ci, vite, Go) ist zu schwer.
- `Dockerfile` kann bereits mehrere Plattformen (`docker buildx build --platform linux/amd64,linux/arm64`), Distroless nonroot, Volume `/data`.
- `.github/workflows/release.yml` läuft bei Tag `v*` und hängt Binaries an den GitHub-Release; ein Image-Schritt fehlt.
- **Domänen-Ausnahme (INF):** Diese Session darf `.github/workflows/release.yml` ändern; sie gilt durch die Freigabe der Sprint-Spec (`docs/arbeitsweise.md` › Domänen).
- Registry: GitHub Container Registry `ghcr.io/tenvan/k3c-family` (Entscheidung steht in der Sprint-README › Offene Fragen, bis dahin Vorschlag). Anmeldung in der Pipeline mit `GITHUB_TOKEN` (Berechtigung `packages: write`).
- Das Image bleibt bei Fehlern des Updates nutzbar: Compose startet erst nach erfolgreichem `pull` neu; das vorige Image bleibt lokal liegen (B-035 › Ausnahme- und Fehlerfälle).

## Erlaubte Dateien

- `.github/workflows/release.yml`, `compose.yaml`, `Dockerfile` (nur falls für Mehrplattform-Build nötig), `README.md` (Abschnitt Docker)
- `docs/sprints/`, `docs/backlog/` (nur Status und Tickets)

## Nicht-Ziele

Einrichtung des Pi, Lastmessung, Änderungen am Go-Code, Server-Suche (B-040), neue Abhängigkeiten im Repo (GitHub Actions `docker/*` sind CI-Schritte und brauchen die Freigabe der Spec).

## Schritte

1. `release.yml`: Schritte `docker/setup-buildx-action` (QEMU ist nicht nötig: das Dockerfile baut Go per Cross-Compile mit `--platform=$BUILDPLATFORM`), `docker/login-action` (ghcr, `GITHUB_TOKEN`), `docker/build-push-action` mit `platforms: linux/amd64,linux/arm64` und Tags `v*` und `latest`; `permissions` um `packages: write` erweitern, `VERSION` als Build-Argument.
2. `compose.yaml`: `image: ghcr.io/tenvan/k3c-family:latest`, `build: .` bleibt für lokale Builds (`docker compose build`), kein `pull_policy` (Update nur per ausdrücklichem `docker compose pull`). Kommentar oben: Update = `docker compose pull && docker compose up -d`.
3. `README.md` › Docker: Start auf dem Pi (`docker compose up -d`), Update (`docker compose pull && docker compose up -d`), Rückfall auf das vorige Image (`image: …:<alter Tag>`).
4. `task check` grün. Das Workflow-YAML mit `actionlint` prüfen, falls vorhanden; sonst Syntax mit einem YAML-Parser. Es wird nichts gebaut und kein Docker gestartet (🧑, 2026-10-02). Das Veröffentlichen selbst läuft erst beim nächsten Tag (siehe Ergebnis: AC-02 wird auf dem Pi in SP11.2 bestätigt).
5. Ergebnis, Status `fertig`.

- **AC-02 umgesetzt (Vorbereitung), noch nicht am Pi bestätigt:** `release.yml` baut bei Tag `v*` zusätzlich das Image für `linux/amd64` und `linux/arm64` und pusht `ghcr.io/tenvan/k3c-family:<tag>` und `:latest` (`packages: write`, Anmeldung mit `GITHUB_TOKEN`, `VERSION` als Build-Argument). `compose.yaml` verweist auf dieses Image, `build: .` bleibt. README › Docker beschreibt Start, Update (`docker compose pull && docker compose up -d`) und Rückfall (älterer Tag).
- Geprüft: `task check` grün, beide YAML-Dateien parsen. **Nicht** geprüft: Workflow-Lauf, Image-Build, `docker compose config` (auf diesem Rechner ist kein Docker installiert, und es wird bewusst nichts gebaut). Den ersten Tag-Lauf und `pull` am Pi bestätigt 🧑 in SP11.2.
- Abweichung: kein `pull_policy: always`, damit `docker compose up` lokal vor dem ersten Release nicht an einem fehlenden Registry-Image scheitert; Aktualisieren nur per ausdrücklichem `pull`.
- Annahme: Das Paket in ghcr ist öffentlich (Registry-Frage unbeantwortet); bei privatem Paket braucht der Pi `docker login ghcr.io`.
